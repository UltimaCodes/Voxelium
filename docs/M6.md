# M6 — threading

date: 2026-07-21

## what got added

- `jobs/JobSystem`: fixed pool of jthreads (hardware_concurrency - 1 → 11 on this box)
  over a mutex+condvar deque. shutdown is stop_token + notify: workers finish their
  current job and exit, queued jobs get dropped. workers never touch GL.
- gen + mesh moved to workers. each worker owns a thread_local GreedyMesher (24 KB of
  scratch) and quad buffer, reused across jobs.
- one deliberate deviation from the spec: per-chunk state is NOT atomic. workers are
  pure functions (voxels in, results out through two mutexed queues); the main thread
  drains queues and owns every state transition. single writer = no atomics, no torn
  states, trivially reasoned about. the one true cross-thread concern — a mesh job
  reading a neighbor while the main thread wants to unload it — is a per-chunk atomic
  job refcount; eviction defers while refs are held.
- in-flight cap (workers x 6) keeps jobs near the camera instead of racing ahead into
  chunks that'll be stale when it moves. nearest-first both queues.
- uploads (the only GL) stay on the main thread under a 2 ms budget, minimum one per
  frame so a heavy chunk can't wedge the queue.
- teardown ordering instead of locks: JobSystem is declared after ChunkManager in main,
  so its destructor joins all workers before the manager frees anything.

## numbers

- world output byte-identical to M5 (same 2,116 chunks, 266,938 quads, 84.0% smoke
  coverage) — threading changed nothing about results, only where the work runs.
- stress test (new, in --smoke): teleport 16 chunks sideways, re-stream everything.
  **worst single main-thread update cost: 0.96 ms.** flying can't hitch on streaming
  when the whole world re-loading costs less than a millisecond a frame.
- mesh avg 0.050 ms on workers (same as main-thread M5 — the mesher doesn't care).
